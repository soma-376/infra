# 0053. dev 프론트 두 앱을 인증 동시성 검증에 앞서 배치한다

## Status

Accepted — PROJ-243. 사용자가 dev에 먼저 앱 두 개를 실행하고 이후 문제를 해결하는 순서를 요청했다. 실제 배포 완료를 의미하지 않는다.

## Context

기존 dev는 두 AZ에 EC2가 있지만 앱은 2a에 하나만 배치한다. application 모듈의 memberOf 제약 때문에 2c는 앱 트래픽을 받지 않는다. 사용자는 인증 동시성 개선보다 두 앱 배치를 먼저 검증하기로 했다.

## Decision

- prod 단일 앱 정책은 유지한다. dev만 desired=2, distinctInstance, AZ spread를 사용한다.
- 기존 2a·2c EC2에 512MiB 앱 하나씩 배치한다. 고정 hostPort=3000과 ALB 대상 그룹·보안 그룹을 유지하고 대상 등록은 ECS가 수행한다.
- dev min=50/max=100으로 한 개를 유지하며 이전 태스크를 먼저 중지한다. 새 태스크 선기동, AZ 장애 시 한 호스트에 두 앱 배치는 이번 범위가 아니다.
- 기존 BFF의 프로세스 내부 갱신 잠금은 공유되지 않는다. 인증 안전성이 검증됐다고 주장하지 않으며 동시 토큰 갱신·로그인·조회를 배포 후 확인한다.

## Alternatives Considered

- 인증 동시성 해결 후 확장: 인증 위험을 줄이지만 사용자가 요청한 실환경 검증을 늦춘다.
- 동적 포트와 선기동 배포까지 동시 변경: 가용성을 높이지만 이번 배치 변경의 범위를 키운다. 후속으로 분리한다.

## Consequences/Tradeoffs

### Positive

- 기존 두 EC2를 활용해 AZ별 앱 실행과 ALB 분산을 검증한다.

### Negative

- 인증 갱신 경합으로 로그아웃이 발생할 수 있다.
- 배포 중 정상 앱 수가 하나로 줄어든다. 한 호스트 장애 시 다른 호스트에 두 앱을 배치할 수 없다.

## Follow-up

- PROJ-243에서 인증 동시성, 선기동 배포와 실패 시 롤백을 검증한다.

## Acceptance Criteria

PR plan에서 EC2 교체가 없는지 확인하고 부수적인 태스크 정의 변경도 검토한다. 실제 적용은 리뷰·머지 후 CI에서 수행한다. 두 EC2별 앱 태스크와 ALB healthy를 확인한다.
세션 오류가 확인되면 dev desired=1, memberOf 2a, min=0으로 복구하는 PR을 적용한다. stickiness를 인증 동시성 해결책으로 사용하지 않는다.
