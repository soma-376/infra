# 0061. dev 프론트는 동적 포트로 새 태스크를 먼저 띄운 뒤 교체한다

## Status

Proposed (PROJ-328; 로컬 구성·mock test, 실제 적용·교체 측정 별도) — ADR-0053의 배포 비율·`distinctInstance`·고정 hostPort 결정을 대체한다.

## Context

- ADR-0053은 dev 앱 두 개를 desired=2, min=50/max=100, `distinctInstance`, AZ spread, 고정 `hostPort=3000`으로 배치했다. 새 태스크 선기동은 후속으로 미뤘다.
- 이 설정에서 ECS는 기존 태스크 하나를 ALB에서 빼고 드레이닝(30초)·종료한 뒤에야 같은 EC2에 새 태스크를 띄운다. 2026-11-08 배포(프론트 CD 42488479566)에서 이 과정이 한 대씩 두 번 반복됐고, 각 회차의 중지→시작 간격은 55초였다. 배포 단계는 262초로 CD 전체의 약 45%다.
- 한 EC2에 새 태스크와 기존 태스크가 함께 뜨지 못하는 이유는 max 100%, `distinctInstance`, 고정 hostPort 세 가지다. 앞의 두 조건만 풀면 포트 충돌로 배치가 실패한다.
- 2026-11-09 실측값(t4g.small 두 대, ECS 등록 1846MiB/2048 CPU):
  - 프론트 512MiB/512 CPU 두 개와 host-alloy 256 하나의 예약 합계: 1280MiB/1280 CPU
  - 호스트 MemAvailable 7일 최저치: 약 1006MiB
  - 프론트 cgroup 최고치: 약 134MiB(30일, 태스크 26개)
  - OOM: 0건
- 프론트 ALB에는 WAF가 없고 서브넷 NACL은 기본값이다. ALB→대상 포트를 제한하는 것은 SG뿐이다.
- dev BFF는 ADR-0055의 공유 Valkey 세션을 사용한다. ADR-0053이 지적한 프로세스 내부 갱신 잠금 문제는 교체 중 앱이 네 개가 되어도 범위가 같다.

## Decision

- dev 태스크 정의는 `hostPort=0`(동적 포트)을 사용한다. 컨테이너 포트는 3000이며 ECS가 실제 호스트 포트를 instance 대상 그룹에 등록한다. prod(awsvpc)는 3000을 유지한다.
- dev에만 ALB SG egress와 앱 SG ingress에 TCP 32768-65535 규칙을 추가한다. 양쪽 모두 SG 참조로 제한하고 CIDR은 쓰지 않는다. 기존 3000 규칙은 prod와 공유하는 리소스이며, 적용 중 기존 태스크와의 연결을 유지하도록 남긴다.
- dev 서비스는 min=100/max=200을 사용한다. 새 태스크 두 개가 healthy가 된 뒤 기존 두 개를 함께 드레이닝·종료한다.
- dev 서비스에서 `distinctInstance`를 제거하고 AZ spread 전략은 유지한다.
- 드레이닝 30초, health check(15초 간격, healthy 2회), grace 120초, circuit breaker rollback은 변경하지 않는다.
- 서비스 갱신은 새 SG 규칙이 생성된 뒤 수행한다.

## Alternatives Considered

### A. 현재 설정 유지
- 장점: 변경이 없다.
- 단점: 매 배포마다 교체 대기가 두 번 반복되고, 교체 중 정상 앱이 하나로 줄어든다.
- 탈락 이유: PROJ-322 이후 남은 CD 시간의 대부분이 이 대기다.

### B. EC2를 한 대 더 추가하고 `distinctInstance` 유지(max 150%)
- 장점: 평상시와 교체 중 모두 앱이 서로 다른 호스트에 있다.
- 단점: t4g.small 한 대(월 약 $15)가 늘고, 새 태스크를 하나씩만 먼저 띄울 수 있어 교체가 여전히 순차적이다.
- 탈락 이유: 비용 대비 단축 효과가 작다.

### C. t4g.medium으로 교체
- 장점: 호스트당 메모리 여유가 커진다.
- 단점: 프론트 EC2 두 대 기준 월 약 $30이 늘고 EC2 교체가 필요하다. 실측 여유로는 필요하지 않다.
- 탈락 이유: 사용자가 small 유지를 결정했다.

### D. 드레이닝·health check 시간 단축
- 장점: 설정만 바꾸면 된다.
- 단점: 진행 중 요청 중단과 비정상 대상 등록 위험이 커진다.
- 탈락 이유: PROJ-322는 근거 없이 이 값을 낮추지 않기로 했다.

## Consequences/Tradeoffs

### Positive

- 교체가 한 번으로 끝나 dev 배포 단계가 짧아질 것으로 예상한다(약 4분 20초 → 2분~2분 30초, 미측정).
- 교체 중에도 정상 앱 두 개가 계속 요청을 받는다.
- EC2 한 대를 쓸 수 없을 때도 남은 한 대에 앱을 배치할 수 있다. 앱 3개와 alloy를 합쳐 예약 1792MiB/1792 CPU다.

### Negative

- AZ spread는 선호 조건이다. 용량 부족이나 호스트 장애 뒤에는 평상시에도 두 앱이 한 EC2에 몰릴 수 있으며, 이 경우 다음 배포 전까지 그대로 유지된다.
- 교체 중 한 EC2의 여유 메모리가 줄어든다. 두 앱이 모두 512MiB 리밋에 닿는 최악의 경우 약 270MiB가 남는다.
- 앱 SG가 ALB SG에 대해 넓은 포트 범위를 연다. 출발지는 ALB SG로 제한된다.

## Acceptance Criteria

- PR plan에 EC2 교체가 없다. 변경은 SG 규칙 2개 생성, 태스크 정의 revision, 서비스 갱신으로 한정된다.
- 적용 직후와 이후 배포에서 대상 그룹의 healthy 수가 2 미만으로 떨어지지 않는다. 대상 포트가 동적 포트로 바뀐다.
- 교체 중 로그인·조회·토큰 갱신이 유지된다. 실패한 배포는 circuit breaker가 이전 revision으로 되돌린다.
- 캐시가 준비된 dev 배포 3회 이상의 ECS 교체 단계 중앙값을 기존 측정과 비교해 PROJ-328에 기록한다.
- 평상시 두 태스크가 서로 다른 AZ에 있는지 확인한다.
- 롤백이 필요하면 이 PR을 revert해 ADR-0053 설정으로 되돌린다.
